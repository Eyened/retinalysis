# Retinalysis

A research site for researchers and engineers exploring tools, deep learning models and datasets for robust, explainable retinal image analysis.

[Repository](https://github.com/Eyened/retinalysis) · [Website](https://eyened.github.io/retinalysis/)

## Develop and check

Use the Node version in `.nvmrc` and npm. Dependencies and the lockfile are committed.

```sh
nvm use
npm ci
npm start
```

Before submitting changes:

```sh
npm run typecheck
npm test
npm run build
npm run test:browser
```

Install the browser with `npx playwright install chromium` if needed.

## Documentation structure

This is a standard Docusaurus docs site. Edit ordinary pages directly in `docs/`:

```text
docs/
  index.md                 # Home
  software/
    index.md               # Software overview
    retinalysis-vascx.md
    ...
  models/
    color-fundus/
      _category_.json      # Category label and order
      index.md
      av-segmentation.mdx  # Manually maintained page importing a card
      ...
  model_cards/             # Copied Markdown assets, excluded from routes
    av_july24.md
    ...
  datasets/
    index.md
    rav.md
```

Folders define the hierarchy. `sidebars.cjs` uses Docusaurus autogenerated sidebars for Software, Deep learning models and Datasets. The navbar is configured directly in `docusaurus.config.ts`.

Use normal page front matter for `title`, optional `sidebar_position` and, when preserving an established URL, `slug`. Use `_category_.json` for category labels and ordering. Keep drafts outside `docs/` until ready to publish. Overview pages use ordinary Markdown links; update those links when adding or removing manually maintained pages.

`.md` files use ordinary Markdown; `.mdx` is available when a page needs React. The site keeps the standard Docusaurus layout. Scientific images live in `static/img/`, with captions, alt text and attribution directly in the relevant page. Use Markdown links and image paths so Docusaurus can handle the `/retinalysis/` deployment base path and validate links.

## Model cards

The website uses the copied cards in `docs/model_cards/`. Startup, tests and builds work with these files alone; no local sync configuration or source checkout is required.

To refresh cards from another checkout, create the optional, Git-ignored configuration:

```sh
cp model-cards.example.yaml model-cards.yaml
```

Edit the mapping so each destination filename beneath `docs/model_cards/` points to its source card's absolute path on your machine. Configure only cards that the website uses, then run `npm run models:sync` explicitly.

The sync tool copies full files byte-for-byte, including YAML metadata. It only writes configured assets in `docs/model_cards/`: it does not generate, overwrite or delete document pages. Removing a configuration entry stops syncing that asset; remove unused copies manually after removing their imports. Keep personal paths in the ignored configuration, not in committed files.

The asset folder is excluded from Docusaurus routes and sidebars. To display a card, manually import it in an `.mdx` document:

```mdx
---
title: A/V segmentation
slug: /models/color-fundus/av-segmentation
sidebar_position: 3
---

import ModelCard from '@site/src/components/ModelCard';
import Card from '@site/docs/model_cards/av_july24.md';

Your own introduction can go here.

<ModelCard content={Card} name="av_july24" />

Your own references or other content can follow.
```

The optional `name` prop displays a model name in a floating top-right tab, with text flowing beside it. Cards use a pale yellow background and no box shadow. Omit it for an unnamed card. The document owns its title, route, sidebar order and surrounding prose. Add, remove or combine imports there to choose which cards are displayed. Sync never changes those choices.

`ModelCard` renders card headings as compact bold inline labels. Each top-level section has at most one **Show more / Show less** control. Sections longer than 280 characters or six lines show a short preview; expanding reveals the whole section, including its paragraphs, lists, code blocks, tables and subheadings. Short and empty sections stay visible. A lone leading H1 is treated as the card title; otherwise the shallowest heading level defines sections. A scoped Markdown transform groups the sections during compilation without changing the copied files. Tables and lists keep their normal Markdown structure. Images become thumbnails that open in a modal with a close button, Escape support and keyboard focus handling. Blank sections stay blank. The card's YAML remains in the copied file and is ignored for page metadata and display.

Use HTTPS image URLs, site images such as `/img/example.png`, or relative image files placed beside the copied card. Docusaurus resolves relative links and images from `docs/model_cards/`. Sync copies only the configured Markdown files; supporting images must be provided separately. It never rewrites the card or copies entire source directories.

```sh
npm start             # Start Docusaurus using the copied cards
npm run models:sync   # Explicitly refresh cards using your local configuration
```

All source paths and destinations are checked before copying; unavailable sources or invalid configuration leave existing files intact and stop the sync command. An empty mapping (`{}`) syncs nothing. Unchanged assets are not rewritten.

Review and commit copied assets alongside the manually maintained pages. `npm run build` and CI use the local copies and do not access source repositories. Editing a document never requires synchronization; editing an external model card does.

## Evidence and historical records

Preserve version-specific evaluation claims and citations when editing documentation. Do not fill missing model-card content automatically. The configured cards currently contain empty sections for their authors to complete.

Keep historical source archives and downloaded papers outside the website repository. Cite the public source and relevant version alongside each page or figure. The RAV figures correspond to arXiv **2512.17322v2**. Scientific images retain their original attribution; no blanket licence is applied to third-party figures or data.

## Deployment

`.github/workflows/site.yml` runs type checks, tests, the production build and desktop/mobile browser checks. Successful pushes to `main` deploy `build/` through GitHub Pages. Select **GitHub Actions** in the repository's Pages settings.

CI builds this repository alone. It does not need sibling checkouts, local sync configuration, Python, notebooks or AI services. The production base path remains `/retinalysis/`.
